## 2. 必须知道的前提（踩过的坑）

### 2.1 这些 ogv 是 **full-range BT.601**，不是 limited

- 空背景实测 **Y=254, U=V=128**；若按 limited 解读，白色应该是 Y=235。
- 正确转换：`Y = 0.299R+0.587G+0.114B`，`U = 128+(B−Y)/1.772`，`V = 128+(R−Y)/1.402`。
- 反面证据：按 limited 解读去比对 `ending_yui\refrences\` 的底图，残差一直卡在 ~9 且怎么调都对不上；
  改 full-range 后降到 ~3，完整模型 1.6。
- **实践影响**：ffmpeg 默认按 limited 解码这些文件，所以凡是“视频 ↔ 参考图”的比对都必须自己转；
  但只要输出时原样保留 YUV 数值，成品的行为就与源一致（本次所有交付都是这么做的）。

### 2.2 `ffmpeg -ss <t> -i xxx.ogv` 取出的帧**不可信**

Theora/Ogg 用 granulepos 跳帧表示重复帧，输入定位会取到与顺序解码不同的帧。
`ending_matsushita` 和 `sys_ecatch00` 都明确验证过这一点。
**所有分析、抽帧、取样一律用完整顺序解码**：

```powershell
& $FF -v error -y -i $SRC -fps_mode passthrough -pix_fmt yuv444p -f rawvideo "$W\all.yuv"
```

### 2.3 存储帧数 ≠ 时间轴帧数

Theora 会把完全相同的帧折叠（granulepos 跳变）。因此：

- **实际存储帧数**：`ffprobe -count_frames -select_streams v:0 -show_entries stream=nb_read_frames`
- **CFR 时间轴长度**：`ffmpeg -i X -fps_mode cfr -r 30 -f null -`，看 `frame=` 与 `dup=`

例如 `ending_matsushita`：容器声明 263.0 s，存储 7502 帧，CFR 时间轴 7890 帧。

**推论**：喂给 libtheora 的帧数会影响输出时长（末尾连续重复帧会被整段丢弃）。
`sys_ecatch00` 就是靠补帧到 135 帧才让编码器输出到接近原始时长。

#### 2.3.1 ⚠️ 真实时间轴必须用 `pts_time`，不能用 `存储帧号/30`

`letter_iwasawa` 第一版就是在这里出错的：容器声明 126.167 s，但只存了 3442 帧，
于是被当成 “114.70 s 的 CFR”。实际上 **336 个槽位是“重复上一帧”**，存储帧号与真实播放
时间是 **1.098 : 1** 的关系，段边界差得很远（插画段的真实起止是 33.03–114.47 s，
而不是 27.8–110.0 s）。后果是成品比源短 11.4 s、整段快 9%。

正确做法：

```powershell
# 1) 取每一存储帧的真实 PTS
& $FP -v error -select_streams v:0 -show_entries frame=pts_time -of csv=p=0 $SRC > pts.txt
# 2) 槽 -> 存储帧 映射：slot = round(pts*30)，其余槽位显示上一帧
#    （见 letter_iwasawa\_work\cfrmap.py，产物 cfr_map.npy）
# 3) 渲染时按槽写帧（重复的帧直接重复写出），再把 3778 帧喂给编码器
```

**只要按槽输出 3778 帧，libtheora 会自动折叠重复帧并保持 granulepos 跨度**，
成品时长就能落在 125.8 s（源 126.2 s），不再出现“少 11 s”的问题。

### 4.5 `letter_iwasawa\ef_iw_letter00.ogv` — 滚动字幕去除（2026-10 重做，第 2 版）

> 本节已按 2026-10 第二轮的处理**整节重写**；第一版的结论（“参考图无法用于重建”、
> “只能用片内干净帧+掩码修补”）已被推翻，原因见下。

#### 4.5.1 时间轴：不是 n/30（第一版在这里搞错了）

源仍是 Theora 1280x720 yuv444p / 30 fps / **Ogg 存 3442 帧**，无音频。
容器声明 **126.167 s**（granulepos 到 3785 号槽）——第一版把“3442 帧”当成 114.70 s 的
CFR 时间轴，其实是错的：**336 个槽位是“重复上一帧”**，存储帧号与真实播放时间是 1.098 : 1。

用 `ffprobe -show_entries frame=pts_time` 取到真实时间轴（`_work\pts.txt`、
`cfrmap.py` → `cfr_map.npy`，3778 槽 ↔ 3442 帧）：

| 真实时间 | 槽 | 存储帧 | 内容 |
|---|---|---|---|
| 0.00–4.90 s | 0–147 | 0–64 | 纯白 + 静态字幕 |
| 4.93–30.60 s | 148–918 | 65–835 | **平移天空**（淡入 65–107、淡出 809–836）+ 滚动字幕 |
| 30.63–33.00 s | 919–990 | 836–873 | 纯白 + 静态字幕 |
| 33.03–114.47 s | 991–3434 | 874–3317 | **插画段**（4 张底图、缩放平移旋转、交叉溶解）+ 滚动字幕 |
| 114.50–125.90 s | 3435–3777 | 3318–3441 | 纯白 + 静态字幕 + 片尾署名 |

用户给的 0–4 s / 4–30 s / 30–33 s **与实测完全吻合**（说的“94 s 以后是白色”实为 114.5 s）。
**成品必须按 3778 槽的 CFR 序列输出**，否则整段会快 9%、时长少 11.4 s。

#### 4.5.2 素材真相 + 关键结论：回忆滤镜在**底图坐标系**

- `refrences\00NNNN.png`（4 张）**就是视频帧本身**：`001167`=存储帧 1049、`001576`=1458、
  `002160`=2042、`002810`=2692（文件名 = 存储帧号 + 118），RGB 逐像素相等（max|Δ|<0.5），
  即这 4 帧**完全没有字幕**，是精确真值。
- `refrences\raw_color\eviw_XXXX.png` 是同一画面的**未加“回忆滤镜”版本**。
- **滤镜坐标系判定（决定性实验）**：以锚帧为源预测同底图其它帧，
  - 屏幕坐标固定的逐像素增益模型 → 残差 **36–44 rms**；
  - 底图坐标的相似变换搬运模型 → 残差 **2.3–16 rms**。

  所以 `frame = white + A(u)·(P(u) − white)`，`u` 为底图坐标 → **可以在底图坐标里做时域融合**。
  第一版认为“画面上盖了空间变化的白色辉光、参考图无法配准”——那是因为没把滤镜放在底图坐标里看。
- 滤镜强度还会**随时间缓慢漂移**（相对底图 MOSAIC 的全局系数从 0.90 变到 1.09），
  且漂移的空间部分不是纯标量；渲染时再叠一层**平滑屏幕增益场 R(x,y)** 吸收它。

#### 4.5.3 做法

1. **几何**：每帧对 4 张 raw_color 底图做 SIFT + RANSAC 相似变换（存 `geo_full.npz`），
   再用 41 帧局部三次多项式平滑（先用局部中值剔除退化拟合）。四段位姿：

   | 底图 | 区间（存储帧 / 真实秒） | scale | rot | 交叉溶解 |
   |---|---|---|---|---|
   | 0801 | 874–1420 / 33.0–51.3 s | 1.58→1.32 | +1.7°→−1.7° | 1385–1465 |
   | 0301 | 1420–1985 / 51.3–70.1 s | 1.07→1.28 | +0.4°→+4.7° | 1955–2025 |
   | 0401 | 1985–2560 / 70.1–89.3 s | 1.300 恒定 | 0.00° 恒定（纯平移） | 2515–2615 |
   | 0701 | 2560–3317 / 89.3–114.5 s | 1.49→1.34 | −4.9°→−2.6° | — |

   溶解权重 α 逐帧最小二乘求出，单调下降无跳变。
2. **底图重建**（`mosaic5.py` → `mosaic6.py`）：回忆滤镜是**深色字形 + 亮色描边**，
   字幕压在深色画面上会留下一圈**比背景更亮**的晕。第一版用“时域中值”仍然脏，
   原因是**字幕在屏幕上几乎不动，而对 0801/0701 这两段，屏幕那个位置对应的底图坐标也几乎不动**
   （0801 从 n=900 到 n=1400，屏幕中心映射到底图只走了 (589,306)→(567,320)，约 25 px，比字高还小），
   于是底图里那些像素被字幕覆盖的帧数超过一半，**中值取到的就是字幕**。
   最终改用**每张底图自己的“绝对干净锚帧”**定位字幕：

   ```
   对底图 k 的每一帧 n：
       A_n  = warp(锚帧_k, M_n ∘ M_anchor^-1)      # 该帧真值背景（无字幕）
       mask  = |F_n − A_n|max > 22                # 锚帧覆盖处，可靠
       mask |= |F_n − bg_模型|max > 26             # 锚帧没覆盖到的边缘，退回模型
       mask 膨胀 3 px
       把 F_n（按全局系数归一化）加权累加进底图，权重 = 1 − mask
   迭代 3 轮，同时输出每像素累加权重 mosweight_*.npy
   ```
3. **天空段**：沿用上一轮重建的 `sky_mosaic_full.png`（1280×1162），逐帧在屏蔽字幕带后
   联合拟合 `(dy, γ)`，`frame = white + γ·(mosaic[y+dy] − white)`，**残差均值 1.17 rms / 最大 2.24**。
4. **替换范围**（`measure_band3.py` 统计了 1090 帧的字幕像素行/列分布）：

   | 区段 | 行框 | 列框 |
   |---|---|---|
   | 插画段 | **325–400** | 80–1200 |
   | 天空段 | **318–402** | 80–1200 |

5. **渲染**（`render_full.py`）：`bg0 = white + Σ α_k·(mosaic_k 经 M_k 变换 − white)`；

## 6. `-g 1`（每帧强制关键帧）与 Theora 重复帧折叠

### 6.1 结论：可以规避

libtheora 会把与前一帧相同的帧标记为“重复帧”而不发 packet，靠 granulepos 跳变让解码器补帧。
给 ffmpeg 传 **`-g 1`**（每帧都是关键帧）后，编码器**不能再把该帧丢成重复帧**，实测：

| 设置 | packet 数 | 末包 pts | 容器时长 | 大小 | PSNR（对无损母版） |
|---|---|---|---|---|---|
| 默认（当前交付） | 44 | 4.4333 | 4.4667 | 590,689 B | 42.05 dB luma / 45.50 avg / min 34.15 |
| `-g 2` | 88 | 4.4333 | **4.5000** | 2,354,699 B | — |
| **`-g 1`** | **135** | 4.4667 | **4.5000** | 4,471,398 B | **59.49 dB luma / 58.47 avg / min 56.72** |

（测试素材：`sys_ecatch00_cn_lossless.mkv` 解出的 135 帧，`-q:v 10` 固定。）

`-g 1` 时 packet 数 = 输入帧数，且每包都带 `K`（关键帧）标志，容器时长与输入严格一致（4.5000 s）。

### 6.2 两个重要推论

1. **重复帧折叠本身是无损的**：解码器会重复上一幅画面，中间段的丢弃不损失任何画质，
   唯一副作用是**末尾**连续重复帧会让 granulepos 跨度提前结束（因为没有后续 packet 承载跳变）。
   所以这从来不是画质问题，只是时长/兼容性问题。
2. **`-g 1` 同时大幅提升画质**：42.05 → **59.49 dB**（最低帧 34.15 → 56.72）。
   原因是全关键帧下每一帧都独立按 q10 编码，不再受帧间预测的量化限制。
   **我先前“42.1 dB 已是天花板”的说法应作废。**
   代价是体积 7.6×（0.59 MB → 4.27 MB）。

### 6.3 何时值得用

- **值得**：短视频、静态画面占比高、或需要逐帧 packet 与输入严格一一对应（naive 工具按 packet 数读帧时会数错）的场合。
- **不值得**：长视频且结尾有大段静止画面（如 `ending_yui` 结尾 86 s 纯白、`ending_matsushita` 的长静止段），
  全关键帧会把本来几乎不占体积的静止段逐帧编码，体积膨胀明显。
  实测 `letter_iwasawa` 3778 帧：默认 **58.3 MB / 125.77 s**（源 27.6 MB），
  `-g 1` 会涨到 **294 MB**，所以这一部也用默认。

### 6.4 关于是否改用 `-g 1`

只需在原命令上加一个参数，其余不变：

```powershell
& $FF -v warning -y -f rawvideo -pix_fmt yuv444p -s 1280x720 -r 30 -i "$W\out.yuv" `
   -c:v libtheora -q:v 10 -g 1 -pix_fmt yuv444p "$dst\xxx.ogv"
```

**已决定：不重出。** 用户已明确“不用动”——几个 ending 后续会在 `.mkv` 基础上继续编辑，
`sys_ecatch00_cn.ogv` 是直出成品且保持现状。第 6 节仅作为技术结论存档。
